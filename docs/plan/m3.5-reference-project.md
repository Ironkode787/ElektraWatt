**Status:** design, its choices decided (section 7), being built · **Backlog row:** FT-1816 · **Counted at:**
`ff5078a92`, 2026-11-20

The reference project (`golden/J-E-2416.ew`, "Golden A", [doc 20](../design/20-golden-project.md)) was the result to
build towards. The program can now make such a cabinet itself, and the persona runs check the window better than
the reference's oracle did, so it goes (owner, at the fourth candidate of 0.3.0). This design says what ends with
it, what moves to a small project the program makes from a script, in which order, and what that buys. Every count
comes from the code at the commit above. A count that is an estimate says so.

## 3. The replacement

**One project, the sample.** Two more fixtures sit beside it: the built-in new project for class (a), and
`release-min` for the release and revision tests (section 4). A second, smaller drawn project would need a script
of its own and a choice per test. The needs found in the sample above are spread over every area (contacts on
other pages, strips, cables, PLC, fluid, layout, macros, reports), and a read-only test does not copy the sample at
all.

**The script.** `fixtures/sample/sample.uiscript` is a UI script (`ew.uiscript/1`) of the window's own actions,
the actions the persona runs and the owner use: the new-project wizard (sections, frame, the standard report layout
of `wizard_data.rs`), `page.new`, `place.pick` by generic part number, `nav.goto` to a cell (`101-E15`), the wire
tool, and the strip, cable, PLC, fluid and layout actions. It uses `command.run` only where the window has no action.
It writes no IDs, and no millimetre position where a cell or a tag will do. If an item needs a command the program
does not have, the item is left out and reported; no feature is built for the sample.

**Committed, generated and checked.** The folder `fixtures/sample/sample.ew/` is committed. The test
`sample::the_committed_sample_is_what_its_script_makes` in `ew-viewmodel`'s `it` binary runs the script in a
headless shell with a seeded ID source (`set_id_source_for_tests`, feature `testkit`) and no date, saves into a
temporary folder, and compares every file with the committed folder byte for byte. With `EW_BLESS=1` it rewrites the
folder, and `cargo xtask gen` runs it: one entry in `xtask/src/generate.rs`, as `actions.txt` has. The other choice
was to generate the sample at test time and cache it under `target/`, keyed by the hash of its script and the
format version. I chose the committed folder for these reasons:

- The crates below the view-model need the files on disk and cannot run the window's script: `ew-store`,
  `ew-format` (permissive), `ew-import-tables` and `ew-api`. The release ships the sample, and the tutorials open
  it.
- A cache keyed by the script and the format version goes stale when a command changes what it writes while neither
  key changes. Tests would then run on a project the code no longer makes. A key of the program's build would make
  each test binary regenerate it after every build, under a lock shared between processes.
- The diff noise is small. The folder changes only when the script or the stored records change: the reference's
  folder changed in 23 commits in three weeks, against 73 for its expected outputs. A change in the drawn output
  does not touch the folder.
- The milestone's rule is against hand-kept copies. This folder is written by `gen` and checked by a test, like the
  QET symbol edition and the generated reference pages. Section 7 asks the owner to confirm this.

**Content, page by page.** The parts are only the starter library's generic parts (`EW-GEN-…`). Parties are
placeholders. The sample is clean under the pre-delivery checks. Its revision is open, because a release needs a
person, so release tests keep `release-min`. Tags print as the default numbering makes them.

**As built (lane 1).** The script is 763 lines; the folder 144 files and 245 KB. It has 27 pages (title page, 7

- 102's contactor has the letter Q (with K, EW-RDS-003 warns); its lamp is in parallel with the coil.
- 103's strip has a fifth terminal SH for the cable's shield, whose wire has a 2.5 mm² override (EW-POT-006 counts

- 104's input is a position switch in the field (the starter push button has one contact). Its outputs drive two
  signal lamps. The valve coils are bound to the outputs of the valve terminal itself, which is on PROFIBUS DP.
- 105 is a new drawn page: bus lines are drawn on bus-topology pages only. Its bus segment runs from the CPU to the
  valve terminal, with addresses and termination set on the ports. It has no plugs, because `bus.cable` takes a plug
  only by its ID.
- 201 gains two silencers on the exhaust galleries; the spare valves' ports are plugged.
- 902 is at the scale 1:5, which the program chose for the plate. Enclosure… placed the legend.
- The revision has no author (only a person at the window sets it); the project's designer is set. No power-supply
  macro was made. The new project keeps the template's pages (`file.new` with `pages`): without them its page 1 gets
  an ID from the system clock, which the seeded test cannot reproduce.
- Under the pre-delivery checks the sample has no error and no warning. It has two infos of EW-NUM-001 on the
  enclosure's tags, which Enclosure… freezes and the numbering cannot derive.

## 6. What it buys and what it risks

**Lines.** About 32,000 lines of tests and tooling go: the runner 7,326; the data tests 9,026; the rehearsal 3,723
and about 2,400 of its support; the translation 1,137; the oracle 1,067; the gpp task 3,863; the generators 3,890.
That is the plan's 30,000. About 12,000 lines of data also go (the expected outputs, the tables, the variants, the
README, the project folder), with 36 pictures and doc 20's 1,767 lines. About 1,000 lines come in: the script, the
small tables and about ten small tests. The (c) tests that only pin again what a lower layer pins are not counted;
step 10 takes up the rest of them.

**Time** (an estimate, not measured). Step 6 measured that copying and opening the reference costs a window test
about 0.5 s and a view-model test 0.34 s (copy 0.125 s, open 0.2 to 0.33 s). From its size, the sample should cost
about 0.15 s to copy and open, about 0.09 s to open read-only in place, and about 0.02 s for a new built-in project.
Summed over the 2,225 tests that reach the reference:

| Binary | Saving |
|---|---|
| window | about 170 s |
| view-model | about 150 s |
| api | about 80 s |
| `ew` (about 300 runs of the program) | about 45 s |
| the rest | about 35 s |

That is about 480 CPU seconds. The deleted (d) tests add about 250 s more: they took 420 s in the baseline run,
before step 6's speed-ups. Together that is about 730 of the suite's 6,300 CPU seconds, or 12 %. The suite keeps the
machine busy, so its wall time should fall in step: about 30 of its 290 s.

**Regenerations that stop.** The 135 expected files of `golden/J-E-2416/expected` stop being regenerated. In three
weeks they changed in 73 commits, with 95 file changes to its pictures, 56 to its page texts and 40 to the
acceptance report. The api's two finding CSVs (7 commits) stop as well. The project folder's 23 regenerations become the
sample folder's, which follow only the script and the stored records. The window's pictures that showed the
reference's pages show the sample's smaller pages instead: there are fewer files per drawing change, but not fewer
regenerations per picture.

**The one thing most likely to go wrong.** Some behaviours are guarded only by an acceptance entry that holds
independent data. Such a guard can be lost without anyone noticing when lane 7 deletes the runner. The likeliest are
the PDF's vector frame, its structure, its text layer and the determinism of the whole export, because no moved test
opens a PDF. The order catches this: lane 4 writes those four tests on the sample in wave 2; lane 7 starts with the
map and the coverage run; and nothing is deleted before both are done.

The second risk is that a move lane blesses a fault of the program into the sample's expected outputs. It is caught
by stating the (c) expectations from the script and by the one look at the sample's frames after lane 1. The third is
that a change to one of the window's actions breaks the script. The sample test then names the failing step, and
`gen` regenerates the folder: a small noise, and an honest one.
