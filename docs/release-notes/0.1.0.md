# ElektraWatt 0.1.0

The release and migration notes of ElektraWatt 0.1.0 (NFR-DOC-07; WP-S6.08 D10).

## 1. What 0.1.0 is

ElektraWatt 0.1.0 is the first release of ElektraWatt, the pilot release of milestone M2: a desktop application for
the electrical schematics of control cabinets, `elektrawatt`, and its command-line program, `ew`, for Windows and
Linux on x86-64. It is meant for the pilot and for anyone who wants to try it on their own projects.

- **Unsigned.** No file of this release is signed: no signed tag, no Authenticode signature on the Windows programs,
  no signed `SHA256SUMS`. Windows may warn before it runs the setup. Check a download as section 2 says instead.
- **No network code.** ElektraWatt makes no network connection of its own: no update check, no crash upload, no
  analytics (`PRIVACY.md`, in the installation and the repository).
- **Supported until the next minor release.** Before 1.0 only the latest 0.x release is supported, until the next
  minor release ([`SECURITY.md`](../../SECURITY.md)).
- **Engineering verification.** ElektraWatt's checks do not replace engineering verification by a competent person.

## 3. What it contains

- **The window**, `elektrawatt`: opens, edits, checks and prints a project. The page list, a zoomable canvas, the
  navigators and their table mode, the properties, find and replace, copy and paste, a history with undo, and named
  workspaces of docked panels. It places devices and symbols, draws and routes wires with interruption points, edits
  terminal strips, cables, black boxes, PLC cards and potentials, and draws the 2D panel layout (enclosures, rails,
  ducts and mounting plates). A first-run flow and a company-standard wizard start new projects; every change is a
  recorded command that a UI script can replay (`elektrawatt --headless --script`). English and Dutch.
- **The command-line program** `ew`: imports QElectroTech projects and CSV tables; checks a project with a check
  scheme; exports PDF/A-2b, SVG and PNG pages, the cable, wire, terminal and part tables as CSV or XLSX (with the
  Excel round trip back into the project), the reports and a read-only SQL projection; prints; applies recorded
  command files; releases revisions; packs a project into an `.ewz` and back; merges a project's files in git with its
  merge driver and resolves the conflicts; upgrades a project of an older format; and answers the public queries.
- **The symbol editor** (Draw ▸ Place ▸ Symbol editor…, or Symbols on the Draw tab): draws a symbol with its
  connection points on the 4 mm grid, its function definition with each pin's mapping and potential role, its text
  slots, its cross-reference anchor and link points, and previews its eight orientations. It saves the symbol to a
  library folder; Draw ▸ Place ▸ Symbol… then places it on a page with the same connection grid, and Test on a new
  page places a copy on a new page with the symbol's grid. New page, and Properties of an empty page, choose a page's
  connection grid: 4 mm or QET 10 px. `ew symbol` does the same work from files, for scripts and AI tools: template,
  schema, validate, import and publish. The project format 0.1 is unchanged.
- **Symbol imports**, in the editor's Open or import and with `ew symbol import`: QElectroTech elements (`.elmt`), and
  EPLAN symbols from EDZ archives, PXF macro exports (`.ema`, `.ems`, `.esl`), parts XML (a generated outline, not the
  macro's artwork) and SLK libraries. An SLK library is read with its `.sdb` drawing tables, in the same folder, and
  without an EPLAN installation. An import gives drafts to review before you save them: what a draft does not carry
  over is listed as a finding, and an EPLAN draft needs its source and licence confirmed. Binary macros are refused,
  and the EPLAN imports are not complete.
- **Outputs**: the reports (parts list, part data, terminal, cable and wire lists, cover tables, back-links and the
  enclosure legend) drawn on report pages and written as PDF/A-2b and SVG, deterministic byte for byte.
- **The project format** 0.1 (section 4): a folder of JSON Lines files that git can diff and merge, saved crash-safe
  with a journal and recovery.
- **The sample project** `J-E-2416.ew`, an anonymised 36-page control-cabinet project, opened read-only (Save as makes
  a copy), and the **user guide** with its tutorials, how-to guides, the reference of every rule, command, dialog and
  panel, and these notes, in English and in Dutch where translated.

## 4. The format

ElektraWatt 0.1.0 writes and reads the project format **0.1** (`"format": "0.1"` in a project's `manifest.json`).
The published schemas of its records are in [`schemas/0.1/`](../../schemas/0.1/index.json).

**Format 0.1 is locked from this release** ([ADR-0011](../adr/0011-format-versioning-and-migration.md) amendment 6).
What that means for the releases after 0.1.0:

- Every later release reads a 0.1 project. Within format 0.1 a later release changes the format only additively: a new
  optional member, a new kind of record, or a new value that this release keeps as it is and writes back unchanged.
  The repository's API guard fails any other change to the published schemas of 0.1 and to the frozen copy of the
  sample project in `fixtures/format/0.1/`, from the tag `v0.1.0` on. It compares each schema's records, members,
  types, required members and values, and every constraint, also of each alternative of a value (a format, a bound, a
  length, a pattern, a count, whether other members are allowed and how their names read, uniqueness): a constraint
  added, removed, tightened or loosened fails, and so does a
  first list of values for a member that had none. A new value needs its line in the release notes since the latest
  release.
- Any other change is a new format version with its migration step: a later release then converts a 0.1 project on
  its first save, after a backup beside the project folder, and its tests open the frozen 0.1 copy.
- A project that a later release wrote in a newer format opens read-only in 0.1.0, or not at all when it needs a
  newer reader; `ew merge-driver` leaves such a project's files as they are.
- A development build that writes a format not yet released marks the project unstable and says so on every save; a
  release opens such a project read-only.

## 5. The derivation and check profiles it ships

- **The derivation profile** `2027.1`: the rules that derive tags, cross-references, potentials, wire numbers and the
  reports from the model. A project names the profile it was derived with; the same model, settings, version and
  profile give the same outputs byte for byte.
- **Wire colour profiles**: "EN 60204-1 machine", "IEC 60445 installation" and "DBU/WH 24 V", the sample project's
  company convention.
- **Wire size profile**: "0.75/1.5", the sample project's company convention; the built-in sizes stay code.
- **PLC address profiles**: Siemens TIA Portal (international) and IEC 61131-3, as library items a project embeds.
- **Check schemes**: `drafting` (the default while editing), `pre-delivery` (the default release scheme), `migration`
  (the check behind an import's migration report) and `full` (every rule). The rule reference in the user guide has a
  page for every rule.

The profiles' sources and licences are in [`content/profiles/README.md`](../../content/profiles/README.md).

## 7. Upgrade steps

- **From an earlier release:** none. 0.1.0 is the first release.
- **Projects of development builds** (the unsigned `0.0.x` builds and the nightly artefacts) are not supported: until
  this release the format changed without migrations, and no pilot-preview project exists to carry over. Start such a
  project again in 0.1.0, or import it again from its QElectroTech source (Project ▸ Import QElectroTech project…, or
  `ew import qet`).

How a project of an older format is upgraded in later releases is in the user guide's
[Upgrade a project](../book/src/how-to/upgrade-a-project.md).

## 8. Known limitations

- **Unsigned files.** Nothing is signed (section 1); Windows SmartScreen may stop the setup until you choose to run
  it. Signed releases come with 1.0.
- **Placeholders of online-only files** (Windows' cloud placeholders, iCloud stubs and other dataless files) are not
  detected: a project in a cloud-synced folder whose files are not downloaded fails to open with a missing file,
  instead of opening read-only with the files named (FT-1293, planned for a later 0.x release).
- **`ew check`** has `--integrity` but not yet its offline mode, `--gate`, `--pages`, `--structure`, `--packs-as-of`,
  `--baseline` and the JUnit and SARIF outputs (FT-1296, planned for a later 0.x release).
- **What comes with 1.0** (decision log ID-1187): signed files, tags and checksums, a second approval of release jobs,
  reproducible builds, the per-machine Windows installer (MSI), the `.deb` and Flatpak packages, the update check, the
  crash report with its upload, the publishing of the libraries on crates.io, and the steward's processes. No macOS
  build is planned before 1.0.
- **Windows and Linux on x86-64 only.** The aarch64 command-line archives that CI builds are not release files.
- **A damaged library copy** is named "the library copy of its part" in its banner and in the Save As refusal, also
  when it is a function definition, a symbol or a profile.
- **The symbol editor's file errors**: a malformed symbol file opened or imported, or an export the file system
  refuses, shows the reader's or the system's own message instead of one in ElektraWatt's words.
- **Place on a new page with its grid** makes the page first, so a placement refused after it, such as a terminal's
  without a strip, leaves an empty page that Undo removes.

## 9. The notices of the AppImage's runtime

The Linux AppImage starts with the AppImage project's static type-2 runtime, release 20251108 (decision log
ID-1275): a separate program at the start of the file, not linked into ElektraWatt. It is MIT-licensed and links
statically musl libc (MIT), libfuse 3.15.0 (LGPL-2.1-only), squashfuse 0.5.2 (BSD-2-Clause), libzstd
(BSD-3-Clause), zlib (Zlib) and mimalloc (MIT). Their notices are in [`NOTICE`](../../NOTICE), and in every
installation; the runtime's source is at <https://github.com/AppImage/type2-runtime>, tag 20251108, commit
dd6cebedcbddde9c82f89b011e8e1d40b6e43868.
